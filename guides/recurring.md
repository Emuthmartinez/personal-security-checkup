# Establish an ongoing routine

A skill file cannot wake itself up, inspect accounts or deliver alerts. A calendar reminder can prompt the person; an agent task can run only within its installed tools and approved scope. Neither proves a review happened. Use provider security/fraud alerts for urgent events; do not wait for the next checkup.

## Choose a loop the host can support

Introduce the routine early, then guide setup one action at a time after the first useful recovery step or when the user asks. At handoff, reach an explicit outcome: installed and delivery tested, saved but delivery unverified, manual only, deferred, declined, blocked or outcome uncertain. Do not require completion of the whole checkup first. Respect a request to stop.

Discover available scheduler/reminder tools, supported cadences, timezone handling, notification destinations, run history and approved access before proposing automation. Read relevant tool/help documentation; do not assume this host behaves like another agent. A host that can send reminders may be unable to execute reviews, access the private note, or inspect accounts. Establish which capabilities exist without requesting broad new access.

Consider these possibilities against actual risk, unresolved work, attention burden and host support. These are choices, not official requirements or four mandatory jobs:

| Cadence | When useful | Bound the work |
| --- | --- | --- |
| Daily | Existing provider alerts, or authorized passive checks of an available signal with a meaningful daily risk | Usually exception-only. Prefer existing alerts; do not create redundant polling. No daily password resets, full audits, document submissions or forced user check-ins. Without supported access, do not invent a daily monitor. |
| Weekly | A temporary unresolved priority or a person who benefits from short sessions | One pending action or small digest; set an end/review condition so resolved work does not keep nagging. |
| Monthly | A short maintenance session suits the person's needs | Rotate one review, such as recovery, important alerts, updates or a harmless backup restore. Avoid a repeated complete inventory. |
| Yearly | A specific renewal, recovery dependency or long-term change warrants review | Reverify the relevant official rule and actual due date. Skip work without a reason; no automatic annual reenrollment or password rotation. |
| Event-driven | New phone/number, move, lost device, recovery change or provider notice | Review affected dependencies promptly. Use existing provider alerts or a supported authorized event trigger; otherwise explain that the user must bring the event back. A scheduled poll is not an event subscription. |

Propose the smallest justified set, often one reminder plus existing provider alerts. State why each selected cadence is useful and omit the rest. Distinguish a reminder to the user, an agent-executed read-only review and a verified fix. Recurring review consent never authorizes future account changes.

Agree on local time/timezone, destination, scope, what can run without the user, access limits, retention, quiet/digest policy, end/review condition and pause/change method. Reuse already specific consent; ask only for missing choices. Show the concrete proposal before enabling anything. Do not create monitoring access, paid subscriptions or new connectors as part of setup. Missing tools or approvals lead to a scoped manual fallback, not a claim of monitoring.

## Portable setup checklist

Use the scheduler's supported UI/API or help. Never invent a product command. Before creation, inspect existing reminders for this purpose with consent so you can update rather than duplicate them. Avoid reading unrelated calendar content.

1. Show the exact proposed reminder/task, recurrence, timezone and notification destination. Ask for approval if not already given. Use a neutral title such as “Personal check-in.” Keep account names and private details out of notifications.
2. For a calendar/reminder app, create the approved cadence at the approved local time; its body can say “Open the private progress note and choose one next step.” This prompts the user and does not run an audit. For a scheduler that supports iCalendar, the recurrence component can be `RRULE:FREQ=MONTHLY;BYMONTHDAY=1`; use the approved day, a future `DTSTART` with the user's IANA timezone and the product's format. Prefer days 1–28 to avoid skipped months. For a task scheduler, adapt the prompt below to a reminder or an authorized unattended review; do not schedule a daily interactive questionnaire when a passive exception check was approved. If timezone/DST handling is unsupported or ambiguous, show the limitation and use a calendar reminder or manual fallback.
3. Read the saved task back from the scheduler. Confirm enabled state, task ID, recurrence, timezone, next run and destination against approval. Configuration text or a successful create call alone is insufficient. If creation has an uncertain outcome, inspect before retrying; do not create duplicates.
4. First check how a delivery test is run and cleaned up. Prefer a documented test/run-now mechanism with no extra persistent task, or a temporary task the host can remove and verify. If deletion is unsupported, explain any retained one-time entry and obtain consent for it before creation, or skip the test and label delivery unverified. With consent, create a harmless one-time delivery test using the same channel and a neutral message, at the earliest supported time or with a supported run-now feature. A temporary test may notify immediately; say so first. Verify scheduler run/delivery status and have the user confirm receipt. A run request alone does not prove delivery. Remove temporary tests where supported and verify removal. If a retained entry was approved, verify it has no recurrence or future run and report that it remains; if this cannot be read back, report the cleanup state as uncertain.
5. Read back the recurring task again after testing; ensure its real next run remains correct. Explain how to pause and resume it. A separate pause/resume test is optional: perform it only when supported and specifically approved, verify readback and restore only the approved enabled state. Otherwise record that it was not tested; do not delete an existing real task merely to test deletion. Record minimal setup metadata privately with permission, including task identity, approved scope, next due, last actual run/review and pause/change steps. On restart, reconcile this record against provider readback before creating or changing anything. Missing task IDs or lost local notes are reasons to search the narrowly scoped existing tasks, not proof that none exists. Across agents, confirm task ownership and reuse its identity; resolve conflicting matches before mutation. After a move or timezone change, verify local time, DST behavior and next due again. Missed periods do not create a backlog of redundant audits.
6. Report the exact state: **installed and delivery tested**, **saved but delivery unverified**, **setup failed**, **outcome uncertain**, or **manual only**; use **deferred**, **declined** or **blocked** when setup has not proceeded. Say whether any test or pending task remains. Never call a future review “completed” based on installation. If a task was created but failed delivery, disable it with authorization or report its exact remaining state; do not silently leave duplicate jobs.

Declining the delivery test is fine: label delivery unverified. A manual fallback is always available: the user adds a neutral calendar reminder themselves, confirms the saved recurrence/timezone/next event, and checks that notifications arrive. If reminders are unavailable, agree a date or habit (“first weekend of the month”) and provide the resume prompt. Say plainly that nothing was installed. No background checking occurs while waiting.

## Tailor the task to its actual capability

Copy only after tailoring to the approved scope. Do not place a private tracker path in a shared task.

> Run one short personal security check-in within the user's approved scope. For an interactive reminder/review, ask whether anything urgent happened; if the user is unavailable, record that it needs them and stop. For an explicitly authorized unattended review, inspect only the named accessible signals and follow the approved exception/digest policy; do not require a user response on every run. Route detected urgent trouble to official recovery help. Never infer account state from user absence. Use only the minimal private progress note the user authorized. Compare dated observations within that scope; distinguish observed, user reported, stale and unknown. Give one prioritized next action and a short done / needs you / not checked summary. Do not sign in, read messages, change settings, send reports, grant access or spend money without exact authorization. Keep secrets, account identifiers and private evidence out of output and notifications. Never mark an unperformed review complete.

## Compare changes and keep notifications quiet

Compare the same scope with a dated baseline. A newly unknown session, recovery change or missed update is a prompt to verify, not automatic proof of takeover. No baseline, missing access or a failed run means **not checked**, not “no change.” Explain the gap and one recovery step. Do not repeatedly scrape accounts or submit identifiers to breach services.

Keep the approved scheduled reminder. For additional agent-generated findings, notify only about a new actionable change, an urgent verified issue, a due user action, or a failed/stale review needing attention. Use the [private action plan](private-tracker.md) to keep one concise actionable digest when daily delivery is justified and agreed. Lead with changed/high-priority actionable items and at most one human handoff. Group routine items into the next digest; on no-change days follow the quiet policy. Do not repeat unchanged permission requests without a material change or agreed review point. Deduplicate by generic item and meaningful state change, retaining the observation date; do not repeat an unchanged warning at every run. Agree when to remind about an overdue action. If a run starts and detects expired account/connector access, report that scoped review as not checked and give a reconnection/manual step; do not expand access or reconnect without approval. A task that never starts or crashes before reporting cannot send its own failure notification. Use and verify native scheduler failure/missed-run notifications if available and approved; otherwise disclose that these failures may go unnoticed and agree on a manual last-run check. Report detected failures neutrally and group repeated unchanged failures into the agreed digest; silence must never be described as a clean review. Do not suppress the bank's or provider's own security alerts.

At session handoff, state the routine type, exact setup/delivery state, next due date and timezone (or manual trigger), last completed review, one remaining setup action if needed, and pause/change steps. Do not describe planned dates as scheduler-confirmed next runs.

Allow pause, reschedule and deletion without guilt. On revocation, stop reading the private note and remove/disable only the task the user specifies; verify provider readback. A deleted reminder does not erase provider-retained chat or notes: explain how the user can remove those separately if requested.
